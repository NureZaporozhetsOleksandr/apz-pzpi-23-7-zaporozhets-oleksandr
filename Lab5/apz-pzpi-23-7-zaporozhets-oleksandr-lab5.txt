     1. Короткий опис проєкту
     Проєкт WorkTime Monitor — це система моніторингу та обліку робочого часу співробітників. Вона призначена для фіксації початку та завершення робочого дня, обліку перерв, перегляду історії робочих подій, формування статистики, адміністрування користувачів та аналізу активності працівників.
Система реалізована як комплексний програмний продукт, що складається з кількох взаємопов’язаних компонентів: backend-сервера, web-застосунку, mobile-застосунку, IoT-компонента та модуля масштабування backend. Backend виконує роль центральної частини системи, яка приймає запити від клієнтів, обробляє бізнес-логіку, працює з базою даних та забезпечує взаємодію між різними частинами проєкту.
     Web-застосунок використовується для роботи співробітників та адміністраторів через браузер. Mobile-застосунок дозволяє користувачу працювати із системою з Android-пристрою. IoT-компонент на базі ESP32/Wokwi імітує фізичний термінал обліку робочого часу, який надсилає події на backend. Також у межах проєкту реалізовано масштабування backend за допомогою Docker Compose, Nginx Load Balancer та навантажувального тестування Locust.
Таким чином, WorkTime Monitor демонструє цілісну систему, яка включає server-side, web, mobile, IoT та інфраструктурні рішення для масштабування.
     2. Мета проєкту
Метою проєкту є розробка системи для автоматизації обліку робочого часу співробітників. Система має спростити процес фіксації робочих подій, надати користувачам зручний інтерфейс для перегляду власної активності, а адміністраторам — інструменти для контролю користувачів, перегляду статистики, формування звітів та аналізу роботи системи.
     Основна ідея проєкту полягає в тому, щоб об’єднати кілька способів взаємодії з системою: через web-застосунок, mobile-застосунок, IoT-пристрій та backend API. Це дозволяє показати роботу системи як повноцінного програмного продукту.
     3. Призначення системи
   Система WorkTime Monitor призначена для організацій, у яких потрібно вести облік робочого часу співробітників. Вона може використовуватися для таких задач:
• фіксація початку та завершення робочого дня;
• облік початку та завершення перерв;
• перегляд історії робочих подій;
• перегляд статистики робочого часу;
• адміністрування користувачів;
• блокування та розблокування облікових записів;
• зміна ролей користувачів;
• перегляд системного аудиту;
• інтеграція з IoT-пристроєм;
• перевірка можливості масштабування backend.
   Система підтримує дві основні ролі користувачів: Employee та Admin. Співробітник може фіксувати власний робочий час і переглядати свою історію, а адміністратор має доступ до розширених можливостей керування системою.

   5. Виконані функції проєкту
   У результаті роботи над проєктом було реалізовано основні заплановані функції.
     5.1 Backend-частина
     Backend реалізовано в минулом семестрі на курсі «Аналіз та рефакторинг коду» на основі Node.js та Express. Він виконує роль центральної частини системи та забезпечує роботу REST API.
Реалізовано авторизацію користувачів, генерацію JWT-токена, перевірку ролей, роботу з користувачами, фіксацію подій робочого часу, перегляд історії записів, роботу з графіками, відсутностями, статистикою, адміністративними функціями та журналом аудиту.
Backend також приймає події від IoT-пристрою та містить endpoint для перевірки стану інстансу під час масштабування.
     5.2 Web-застосунок
     Web-застосунок реалізовано як клієнтську частину системи для роботи через браузер. Він взаємодіє з backend через REST API.
У web-застосунку реалізовано сторінку авторизації, головну сторінку користувача, фіксацію робочих подій, перегляд історії, статистики, профілю, сторінки відсутностей, графіка, адміністративної панелі, звітів та аудиту.
Web-застосунок підтримує різні можливості залежно від ролі користувача та відображає події, отримані від IoT-пристрою.
     5.3 Mobile-застосунок
     Mobile-застосунок реалізовано для Android. Він дозволяє користувачу працювати із системою з мобільного пристрою.
У застосунку реалізовано авторизацію, відображення профілю, перегляд поточного статусу робочого дня, фіксацію робочих подій, перегляд історії, оновлення історії з backend, базову статистику та адміністративну статистику для користувача з роллю Admin.
     Mobile-застосунок не взаємодіє з IoT-пристроєм напряму. Він отримує IoT-події через backend, оскільки всі події зберігаються у спільній базі даних.
     5.4 IoT-компонент
     IoT-компонент підтримує події START_WORK, BREAK_START, BREAK_END та END_WORK. Після натискання кнопки у Wokwi пристрій формує JSON-подію та надсилає її на backend через HTTP POST-запит.
     Backend приймає подію, перевіряє ключ пристрою, перетворює тип події у формат системи та зберігає її у таблиці записів робочого часу. Після цього подія одночасно стає доступною у web-застосунку та mobile-застосунку.
     5.5 Масштабування backend
     Для демонстрації масштабування backend було реалізовано горизонтальне масштабування за допомогою Docker Compose та Nginx Load Balancer.
Було створено три backend-інстанси: backend-1, backend-2 та backend-3. Перед ними розміщено Nginx, який розподіляє запити між інстансами.
     Для перевірки роботи масштабування додано endpoint GET /api/health, який повертає інформацію про те, який backend-інстанс обробив запит. Також проведено навантажувальне тестування за допомогою Locust.

     Основні заплановані функції проєкту були реалізовані. Водночас частина можливостей залишилася як перспектива подальшого розвитку системи:
• розширена аналітика робочого часу з графіками та фільтрами;
• повноцінна система push-сповіщень у mobile-застосунку;
• розширене керування графіками роботи та календарями;
• автоматичне формування PDF/Excel-звітів;
• розгортання системи у хмарному середовищі або Kubernetes-кластері;
• розширення IoT-компонента фізичними сенсорами присутності або RFID-ідентифікацією.
     Ці функції не є критичними для демонстрації основної роботи системи, але можуть бути реалізовані в наступних версіях проєкту.
     7. Архітектура системи
     Архітектура WorkTime Monitor побудована за принципом клієнт-серверної взаємодії. Центральним елементом є backend, який надає REST API для web-, mobile- та IoT-клієнтів.
• Web-клієнт звертається до backend для авторизації, фіксації подій, перегляду історії, статистики та адміністрування.
• Mobile-клієнт використовує той самий backend API для авторизації, фіксації та перегляду подій робочого часу.
• IoT-пристрій ESP32/Wokwi надсилає події на backend через окремий IoT endpoint.
• Backend зберігає дані в SQLite та забезпечує їх доступність для всіх клієнтів.
• Для демонстрації масштабування backend запущено кілька інстансів backend-сервера за Nginx Load Balancer.

Опис реалізованих компонентів
     8.1 Backend
     Backend реалізує REST API, авторизацію за допомогою JWT, перевірку ролей користувачів, роботу з базою даних, обробку робочих подій, адміністративні функції, аудит та прийом IoT-подій. Він є центральною частиною системи, через яку взаємодіють усі клієнти.
     8.2 Web-застосунок
     Web-застосунок забезпечує повний інтерфейс користувача та адміністратора. Він дозволяє фіксувати робочий час, переглядати історію, статистику, керувати користувачами, переглядати аудит та результати роботи системи.
     8.3 Mobile-застосунок
     Mobile-застосунок дозволяє використовувати систему з Android-пристрою. Він підтримує авторизацію, перегляд профілю, фіксацію подій, перегляд історії та оновлення даних з backend, включно з подіями, які були створені IoT-пристроєм.
     8.4 Масштабування backend
     Масштабування backend реалізовано через Docker Compose, три backend-інстанси та Nginx Load Balancer. Це дозволяє показати принцип горизонтального масштабування: кілька копій сервера виконують однакові функції, а load balancer розподіляє між ними HTTP-запити.
     9. Інтеграція IoT-компонента з web та mobile
     IoT-компонент інтегровано з системою через backend API. Пристрій ESP32/Wokwi не звертається безпосередньо до web- або mobile-застосунку. Замість цього він надсилає JSON-події на backend, а backend зберігає їх у спільній базі даних.
     Після збереження у базі даних подія стає доступною для всіх клієнтів системи. Web-застосунок може відобразити її у вкладці історії та змінити поточний статус користувача. Mobile-застосунок може підтягнути ці записи через GET /api/time-entries/my і показати їх у мобільній історії.
     Такий підхід дозволяє підтримувати єдине джерело даних для різних клієнтів системи. IoT-компонент, web-клієнт і mobile-клієнт працюють через спільний backend, тому дані залишаються узгодженими.

     13. Висновок
У межах роботи над проєктом було створено комплексну систему WorkTime Monitor, яка об’єднує backend, web-застосунок, mobile-застосунок, IoT-компонент та рішення для масштабування backend.
Система дозволяє користувачам фіксувати робочий час, переглядати історію, статистику, працювати з профілем, а адміністраторам — керувати користувачами та аналізувати роботу системи. IoT-компонент демонструє можливість інтеграції фізичного пристрою з програмною системою, а масштабування backend показує підготовку системи до роботи з більшим навантаженням.
Не всі перспективні функції були реалізовані повністю, зокрема перехід на PostgreSQL, push-сповіщення, розширена аналітика та хмарне розгортання. Проте основна функціональність системи реалізована, а проєкт демонструє цілісну архітектуру з кількома клієнтами та центральним backend-сервером.
