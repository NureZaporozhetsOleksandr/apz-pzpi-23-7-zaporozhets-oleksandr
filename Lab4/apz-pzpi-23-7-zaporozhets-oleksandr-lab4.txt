     1 Мета роботи
     Метою лабораторної роботи є дослідження та практична реалізація підходів до масштабування backend-частини програмної системи для роботи з більшим навантаженням. У межах роботи необхідно показати, як декілька копій backend-сервера можуть обробляти запити через load balancer, а також провести навантажувальне тестування та проаналізувати отримані результати.
     2 Постановка задачі
     Згідно з умовами лабораторної роботи потрібно показати можливість масштабування backend системи. Для цього було обрано горизонтальне масштабування: кілька однакових екземплярів Node.js/Express backend виконують однакові функції, а запити між ними розподіляються за допомогою Nginx load balancer.
• підготувати декілька backend-інстансів системи WorkTime Monitor;
• налаштувати балансувальник навантаження Nginx;
• додати службовий endpoint /api/health для перевірки роботи інстансів;
• запустити середовище через Docker Compose;
• провести навантажувальне тестування за допомогою Locust;
• порівняти результати для 1, 2 та 3 backend-інстансів;
• проаналізувати вузькі місця системи.
     3 Короткий опис системи WorkTime Monitor
     WorkTime Monitor — це система моніторингу робочого часу співробітників. У попередніх лабораторних роботах було реалізовано backend на Node.js/Express, web-клієнт, mobile-клієнт та роботу з базою даних SQLite. Backend містить модулі авторизації, роботи з користувачами, записами робочого часу, графіками, відсутностями, аудитом та звітами.
     Для лабораторної роботи №4 було використано backend з попередньої реалізації та підготовлено окреме масштабоване середовище у каталозі Lab4/backend-scaling.
     4 Стратегія масштабування backend
     Для системи було обрано стратегію горизонтального масштабування. Вона передбачає запуск кількох однакових екземплярів backend-сервера. Усі екземпляри виконують однакову бізнес-логіку, а клієнтські запити надходять не напряму до конкретного сервера, а до load balancer, який розподіляє їх між доступними інстансами.
     
     Рисунок 4.1 — Архітектура горизонтального масштабування backend
     У тестовому середовищі було використано три backend-інстанси: backend-1, backend-2 та backend-3. Кожен інстанс запускається в окремому Docker-контейнері на внутрішньому порту 3000. Nginx приймає зовнішні запити на порту 8080 і передає їх одному з backend-інстансів.

  backend-2:
    build:
      context: ./backend

    container_name: worktime-backend-2
    environment:
      - PORT=3000
      - INSTANCE_NAME=backend-2
      - JWT_SECRET=worktime-secret
    ports:
      - "3002:3000"

  backend-3:
    build:
      context: ./backend
      dockerfile: Dockerfile
    container_name: worktime-backend-3
    environment:
      - PORT=3000
      - INSTANCE_NAME=backend-3
      - JWT_SECRET=worktime-secret
    ports:
      - "3003:3000"

  nginx:
    image: nginx:alpine
    container_name: worktime-load-balancer
    ports:
      - "8080:80"
    volumes:
      - ./nginx/nginx.conf:/etc/nginx/nginx.conf:ro
    depends_on:
      - backend-1
      - backend-2
      - backend-3
7.3 Конфігурація Nginx
events {}

http {
    upstream backend_cluster {
        server backend-1:3000;
        server backend-2:3000;
        server backend-3:3000;
    }

    server {
        listen 80;

        location / {
            proxy_pass http://backend_cluster;
            proxy_http_version 1.1;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
        }
    }
}

class WorkTimeBackendUser(HttpUser):

     8 Навантажувальне тестування
     Для навантажувального тестування було використано Locust. Тест виконував запити до endpoint /api/health через Nginx load balancer. Для всіх тестів використовувалися однакові параметри: 50 користувачів, швидкість нарощування 5 користувачів за секунду, host — http://host.docker.internal:8080.
     Було проведено три експерименти: з одним backend-інстансом, двома backend-інстансами та трьома backend-інстансами. Для кожного тесту фіксувалися кількість запитів за секунду, середній час відповіді та кількість помилок.

     9 Аналіз вузьких місць системи
     Під час масштабування backend важливо враховувати, що збільшення кількості інстансів не завжди автоматично дає пропорційне збільшення продуктивності. У тестовому середовищі були виявлені такі потенційні вузькі місця:
• SQLite база даних: у поточній системі використовується файлова БД. При великій кількості одночасних операцій запису вона може блокуватися, тому для промислового масштабування доцільно перейти на PostgreSQL або іншу клієнт-серверну СУБД.
• Ресурси локального комп’ютера: усі контейнери запускалися на одному ноутбуці, тому CPU, RAM і дискова підсистема обмежують результати тестування.
• Nginx та Docker networking: частина часу відповіді витрачається на проксування запитів через load balancer та внутрішню мережу Docker.
• Легкість тестового endpoint: /api/health майже не навантажує backend, тому різниця між 1, 2 та 3 інстансами проявляється переважно у зменшенні середнього часу відповіді, а не в різкому прирості RPS.
     Для реального високонавантаженого середовища доцільно винести базу даних в окремий серверний сервіс, додати кешування, використовувати stateless-підхід для backend та контролювати ресурси контейнерів через Kubernetes або іншу платформу оркестрації.

     11 Висновки
     У межах лабораторної роботи було реалізовано горизонтальне масштабування backend-частини системи WorkTime Monitor. Для цього backend було контейнеризовано за допомогою Docker, а для запуску кількох інстансів використано Docker Compose. Перед backend-контейнерами було налаштовано Nginx load balancer, який розподіляє HTTP-запити між декількома копіями сервера.
     Навантажувальне тестування за допомогою Locust показало, що система стабільно обробляє запити без помилок при 50 віртуальних користувачах. При збільшенні кількості backend-інстансів середній час відповіді зменшився, що підтверджує доцільність горизонтального масштабування. Водночас результати також показали, що у локальному тестовому середовищі приріст RPS обмежується ресурсами комп’ютера, Docker/Nginx overhead та простотою тестового endpoint. Основним потенційним вузьким місцем для реального навантаження є SQLite, тому в промисловому варіанті систему доцільно перевести на PostgreSQL або іншу серверну базу даних.
